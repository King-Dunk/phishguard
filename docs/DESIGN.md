# Design decisions (interview-style Q&A)

**1. Why block in code instead of in the prompt?**
A prompt is a request to the model. Model output can be changed by the email it reads, by a poisoned tool result, or by a plain mistake. So the MFA rule lives in `mutating/gateway.py`, and the executor refuses to run without a grant that only the gateway can issue. Whatever the model writes ("MFA already verified") is just text; no code path reads it as permission.

**2. How is read/write isolation enforced, and how do you prove it?**
Two packages. The LLM is only given `ReadOnlyToolbox`, which has three read tools. `tests/test_isolation.py` checks four things: no import of `mutating` in the source of `readonly`, `llm` and `agent` (AST scan); after importing them in a fresh process, no `phishguard.mutating` in `sys.modules`; the whole analysis still works when a `sys.meta_path` hook blocks `phishguard.mutating`; and tool names don't overlap with action names, with mutating tool calls returning errors. Limit: this is import-level separation inside one process.

**3. What counts as a "sensitive" action, and can a harmless-looking action slip through?**
`policy.py` has two rules. Seven action types always need MFA. For every other type, any param key or text (including `reason`) mentioning money or account words (English and Chinese) escalates to MFA, after NFKC normalization and zero-width removal, so fullwidth or zero-width tricks don't hide it. Unknown action names are denied. This is keyword-based, so a paraphrase with no keyword could pass; the safer direction is to add more always-MFA types, not more keywords.

**4. How do MFA timeout and replay work?**
Each pending action has an expiry from an injectable clock. Every gateway call first sweeps expired items to `expired` and writes an `action_rejected (mfa_timeout)` audit event, so a late correct code is rejected (HTTP 410). A pending action is a small state machine (pending, then executed, rejected or expired) behind a lock; only `pending` can execute, so replaying a used code returns 409. Codes are random per pending action, stored salted and hashed, and compared in constant time. Three failures reject the action.

**5. What is the "double check"?**
`/actions` returns a digest of the exact action (type, params, requester). `/mfa/verify` needs that digest and the code. The approver's client has to echo what was proposed, so a swapped or altered action can't ride on a valid code. A digest mismatch counts as a failed attempt.

**6. Why can the LLM only raise the risk score?**
The final score is `max(deterministic score, LLM score)`. If a prompt-injected model says "risk 0", the rule-based floor still stands. The cost is that the LLM can add false positives; for a security tool failing toward caution is the chosen trade. Email text containing injection phrases is also a feature that raises the score.

**7. How do the circuit breakers save money?**
Two limits per request: `max_steps` and a token budget (input plus output per call, summed). Each call's `max_tokens` is capped to the remaining budget. On a trip, the agent stops and returns the deterministic result with `circuit_break` set, so a looping model costs a bounded amount and the caller still gets an answer. Email body is also truncated to 2000 chars in tool output and capped at 20000 on input.

**8. Why a MockLLM, and what does it prove?**
It makes tests free, offline and deterministic (a test blocks sockets and checks the SDK isn't imported). It proves the control flow, limits and security properties, which don't depend on model quality. It does not prove how a real model behaves; `scripts/smoke_real_api.py` exists for that and hasn't been run yet.

**9. How trustworthy are the evaluation numbers?**
Not very, by design. The data is synthetic and the rules and generator share assumptions, so 97% is a regression baseline. The honest weak spot it shows is BEC from a real compromised mailbox, which only wording reveals.

**10. What would you change to run this in production?**
Run `mutating` as a separate service with its own credentials and network policy (the in-process grant is only a guard against accidents and LLM misuse); store pending actions and audit logs durably; use a real MFA channel (TOTP or push) bound to the approving user, with rate limits; add authentication and per-user authorization on the API; validate the detector on real labeled mail; and replace keyword escalation with an allowlist of low-risk actions, so anything not on it needs MFA.

## Production hardening (round 2)

**11. Why parse `.eml` yourself instead of trusting fields the caller sends?**
In production the input is the raw message from the MTA. `readonly/eml.py` uses the stdlib `email` package with `policy.default`, walks multipart trees, extracts plain text, strips HTML to text while keeping each anchor's visible text and real `href`, and records attachment name, MIME type and size without executing anything. Raw size is capped at 2 MB before parsing.

**12. Anyone can write an `Authentication-Results` header. How do you trust SPF/DKIM/DMARC?**
Each hop prepends headers, so the topmost one was written by our own receiving MTA; anything below may come from the sender. The parser uses only the header whose `authserv-id` matches `PHISHGUARD_AUTHSERV_ID`, or the topmost one when that is not set. `phish_forged_auth_header.eml` carries a fake `pass` header under the real `fail` and is still scored as failing. `softfail` and `permerror` count as fail.

**13. How do you catch look-alike domains?**
Three layers on the registrable domain: substring of a trusted domain (`acme-corp.com.secure-login.net`); character normalization (`0→o`, `rn→m`) plus similarity ratio; and Levenshtein distance ≤ 2 for names of at least 6 characters (`acmecrop.com`). Punycode labels are decoded and mixed-script letters (Cyrillic `а`, Greek `ο`, ...) are folded to Latin; if the result is or imitates a trusted domain, that is `homoglyph_domain`, the strongest signal. The same checks run on link hosts.

**14. How does the score stay explainable?**
Each feature has a weight `w`. The score is noisy-OR, `1 - Π(1 - w)`, which equals `1 - exp(-Σ Lᵢ)` with `Lᵢ = -ln(1 - wᵢ)`. Each feature's contribution is `score × Lᵢ / ΣL`. The contributions are exact, independent of feature order, and add up to the score, so the API can say "homoglyph_domain +54.7, payment_keywords +13.3 = 68.0". A plain weighted sum would also be additive, but it would exceed 100 and lose the "independent evidence" reading.

**15. Why TOTP, and how is replay prevented?**
TOTP needs no SMS provider and works offline in any authenticator app. A code is valid for its whole 30 s step (±1 step for clock drift), so it could be replayed. The manager stores the last accepted step per user and only accepts a strictly newer one, which burns the current and every older step. The step is stored in SQLite, so a restart does not reopen the window. A TOTP step is only consumed when the action digest also matches, so a typo in the digest does not waste a code.

**16. Why two failure limits (3 per action, 5 per operation)?**
Three bad codes reject one pending action, but an attacker could open a new pending action and keep guessing. So failures are also counted per operation (requester + action type) across pending actions. Five in a row lock that operation for 15 minutes, write `operation_locked` to the audit log, and return 423; while locked, attempts are recorded as `operation_blocked`. A success resets the counter. Locking per operation instead of per user means an attacker hammering `transfer_funds` cannot block the user's other work.

**17. What does the hash chain prove, and what doesn't it?**
Each entry stores the previous entry's SHA-256 and its own hash over canonical JSON. Editing, deleting or reordering any row breaks the chain at that row; re-hashing one edited row breaks the next link. `verify_chain()` checks both memory and the SQLite copy and `first_broken()` names the row. It does not stop someone who can rewrite the whole table and recompute every hash. For that, periodically publish the latest hash somewhere the attacker can't write (a WORM bucket, a separate log service, or a signed checkpoint).

**18. Why API keys, and why constant-time comparison?**
It's the simplest service-to-service auth that a mail gateway or SOAR tool can use. The presented key and every stored key are SHA-256 hashed and compared with `hmac.compare_digest`, and the loop never exits early, so response time reveals neither a matching prefix nor which key matched. The server refuses to start without keys unless `PHISHGUARD_ALLOW_NO_AUTH=1` is set (fail closed). Limit: keys identify a client system, not a person; `requested_by` should come from SSO in production.

**19. How does the rate limiter work and where does it break?**
A sliding-window log per bucket: a deque of timestamps, at most N per 60 s, answering 429 with `Retry-After`. Valid keys get a bucket per key; failed auth gets a bucket per client address, which slows key guessing. Idle buckets are evicted when the table is full, so memory is bounded. It is per process: with several workers the effective limit multiplies. The fix is Redis with an atomic counter.

**20. Why SQLite and no ORM?**
The data is four small tables (pending actions, audit, TOTP, lockouts) and the queries are key lookups and appends. `sqlite3` is in the standard library, adds no dependency, and runs in WAL mode with `synchronous=FULL` so an audit row survives a crash. One connection behind a lock is enough at this scale. The store has no update or delete method for audit rows. For several instances, the same interface maps to Postgres.

**21. What is the hybrid mode for?**
Cost. Rules cost nothing and decide the clear cases. The LLM is only called when the rule score is in the gray zone (30-70), so spending follows the share of ambiguous mail, not total volume. `evaluate.py` reports accuracy, precision, recall, F1, latency, LLM call rate and cost per 1000 mails for `rules`, `llm` and `hybrid`. Prices are CLI inputs, not hard-coded, and the LLM modes only run with `ANTHROPIC_API_KEY`; CI runs `rules` only. On the synthetic set, 16.7% of mail is in the gray zone and all 16 rule misses are in it.

## Red team and self-improvement (round 3)

**22. How does the red team decide that an attack "failed"?**
Not by status codes alone. After every payload the runner checks invariants with oracles that see inside the system: the executor ledger (any money/account action without an approval the runner made itself is a bypass), a wrapper around the SQLite connection that records every statement (each one must be a string literal from `store.py`, so attacker text can never have become SQL), `PRAGMA integrity_check` plus the table list and audit chain, response headers, files in the sandbox directory, and `/health`. The model in the loop is deliberately compromised: it obeys the mail and calls money tools. A breach means an invariant broke; a detection miss is tracked separately.

**23. Why both Docker and in-process modes?**
Docker answers "what can an attacker reach over the network from a separate box": the API container is non-root, read-only, capability-free, resource-limited and on an `internal` network without egress (checked from inside the container). In-process answers "did anything bad happen inside", because only there can the oracles read the ledger and wrap the database. pytest uses in-process so CI needs no Docker. Both modes ran with the same totals.

**24. Which finding mattered most?**
Deeply nested params. The content-based MFA escalation walked params only 6 levels deep and treated "couldn't look" as "nothing there", so `send_reply` with an IBAN 8 levels down executed without MFA. The fix flips the default: anything the policy can't fully inspect requires MFA, and the API rejects such bodies early. The general lesson: every limit in a security check must fail closed.

**25. Why normalize user identities in the gateway?**
`requested_by` is a string. "Alice" and "alice" were different users, so the capitalized one had no TOTP enrollment and fell back to the development code channel, and it had its own lockout counter. Identities are now NFKC-normalized, casefolded and stripped of zero-width and bidi characters in one function used by the gateway and the TOTP store.

**26. How do you know the SQL is parameterized, not just believe it?**
Code review says every query uses `?` placeholders. The red team proves it at run time: the recorder logs the SQL text of every `execute`, and the oracle requires each to be exactly one of the literals parsed out of `store.py` with `ast`. If anyone ever builds SQL with an f-string, the injected statement isn't in that set and the oracle fails, whether or not the injection "worked".

**27. Why can't improve.py change the MFA gateway, even if a human would approve?**
Because its inputs are attacker-influenced (missed phishing, mutated attacks, optional LLM output). A poisoned input could steer a "fix" that weakens the gate, and a human reviewing a long diff can miss one changed comparison. So the boundary is in code: `check_patch` refuses any diff naming a protected path (normalizing `..`, case and diff prefixes, handling renames and binary diffs), and refuses diffs it can't parse. Changes to the gateway are still possible, but only written by a person. improve.py also never applies anything; tests check that a run leaves every source file byte-identical.

**28. How is the $2 LLM cap made hard?**
Each call is checked before it is sent, against its worst case: input bytes (a token is never fewer than one byte) plus the full `max_tokens`. Actual usage is charged after; if a provider ever bills more than the bound, the loop stops. `--budget` can only lower the $2 ceiling, and without explicit prices the LLM step doesn't run, because a dollar cap can't be enforced against unknown prices.

**29. What did self-improvement teach about itself?**
On the synthetic data, the top "phrases common to misses" included "it's sarah" and "it's david": names from the generator's templates. A tool that auto-merged that rule would have overfitted to the test data. The proposal shows the evidence and the simulated effect (7 of 18 misses rescued, 0 legitimate samples matched), and a human has to judge whether the phrases are real signal.

**30. Why ship the public-dataset script without results?**
The build environment's network policy blocks both corpus hosts. The script, loader and comparison table are tested offline with a mocked download. The README states the expected direction of the synthetic-vs-real gap and marks it as unmeasured, rather than inventing numbers.

## Real-corpus calibration (round 4)

Evidence: `docs/real_corpus_error_analysis.md`, aggregate statistics from a local run of the previous version on 15,721 real messages (SpamAssassin easy_ham/hard_ham, Nazario phishing; no message content). Baseline (rules, threshold 50, whole corpus): accuracy 64.4%, precision 87.7%, recall 60.0%, F1 71.2%; false-positive rate 22.7% on easy_ham, 34.4% on hard_ham. Below, a feature's *likelihood ratio* (LR) is its fire rate on phish divided by its fire rate on ham. LR near 1 means the feature carries no information, whatever its weight.

**31. Why split `suspicious_link`, and why is its generic part weighted 0?**
It fired on 82.6% of ham and 84.3% of phish (LR 1.02), on 99.6% of false positives, and added about 23 points each time. The most common false positive (394 of 970) was exactly `no_authentication + reply_to_mismatch + return_path_mismatch + suspicious_link`, and with the old weights that is 1 - 0.92·0.70·0.88·0.70 = 60.3%, the measured FP median. "The link goes to a host other than the sender's" describes nearly all real mail (newsletters, list archives, CDNs). The specific mechanisms that phishing uses and normal mail almost never does are now separate features with their own weights: IP-address hosts (including integer/hex forms), shorteners, a known brand as a host token on a domain the brand doesn't own, non-standard ports, `user@host` obfuscation, `data:`/`javascript:` URIs and punycode hosts. The generic part survives as `unrelated_link_host` with weight 0, so it is still extracted and calibration can give it weight again if dev data ever shows it is informative. Each link signal counts once per message, so 50 links can't stack. Brand ownership lists are domain knowledge, not fitted to Nazario, though Nazario's PayPal/eBay focus means real-corpus recall will flatter this feature somewhat.

**32. Why treat list mail differently for Reply-To and Return-Path, and why not exempt it fully?**
`reply_to_mismatch` fired on 18.3% of ham vs 7.8% of phish (LR 0.43) and on 75.9% of false positives; `return_path_mismatch` on 69.2% vs 20.7% (LR 0.30) and 85.3% of false positives. On this corpus both point toward *legitimate* mail, because mailing lists set Reply-To to the list and use their own bounce address (and 80.1% of false positives had Reply-To set, vs 12.7% of true negatives). Now: a same-organization address (same registrable domain) never counts; when `List-Id`, `List-Unsubscribe`, `List-Post` or `Precedence: list|bulk|junk` is present, Return-Path mismatch is ignored and Reply-To mismatch drops to 0.03; Return-Path drops to 0.04 overall (ESPs legitimately bounce elsewhere). These headers are sender-controlled, so a phisher can add them. The defense is that they only soften the generic mismatch: a corporate sender whose replies go to free mail (the BEC pattern the synthetic set is built on) keeps a strong weight (`reply_to_freemail`, 0.35) with or without list headers. The feature *name* stays `reply_to_mismatch` for API compatibility; the weight key (`Feature.key`) records which case fired.

**33. Why is `no_authentication` nearly zero?**
It fired on 100% of ham and 86.3% of phish (LR 0.86). SpamAssassin ham is from 2002, before DKIM (2007) and DMARC (2012); the phishing spans later years. The feature mostly measured the *year*, and a model trained on it would learn "old mail is safe", which is useless on today's mail. The weight is now 0.01 so it can't push anything over the threshold. The README states this dataset bias. Explicit *failures* (`auth_fail`) are unaffected; they mean something in any era.

**34. Why these attachment signals and weights?**
18.2% of false negatives carried an attachment that was not flagged, vs 7.4% of true positives, and ham almost never has attachments (0.5-0.7%), so the cost of new attachment signals on this ham is small. But that is also why their false-positive cost on modern ham can't be measured here, so they get moderate weights. `risky_attachment` (0.40) now covers more executables/scripts (`.pif .com .jse .vbe .wsf .msi .cpl .xll .chm`), disk images, html/svg/one, macro documents, and a broadened double extension (`.pdf.exe`, `.jpg  .scr`, `.pdf.html`). New: `archive_attachment` (0.20, content the gateway can't scan), `office_legacy_attachment` (0.12, `.doc/.xls/.rtf` can carry macros), `encrypted_attachment_hint` (0.35, "password: 4471" or "password-protected zip" *with* an attachment; the classic way to get a payload past scanners), and `image_lure` (0.15, image-only mail with almost no text).

**35. Why change the prompt-injection patterns on a real-corpus round?**
`prompt_injection_attempt` fired on 0.6% of ham and 0.1% of phish (LR 0.17, i.e. worse than useless) and sat on 2.4% of false positives. The cause is mailing-list language: "you are now subscribed" matched the bare `you are now`, and "as root" / "as the developer" matched `as (the) root|developer` in the Linux lists that make up SpamAssassin ham. Both now need a role-change context ("you are now an unrestricted AI", "acting as the system"). The red-team suite, which contains the real injection payloads, still passes 12/12.

**36. Why a weights file instead of constants?**
Calibration is a data task, not a code change. `phishguard/readonly/weights.yaml` holds every weight and the brand table. `load_weights()` validates it (every value in [0, 0.95]; a feature with no weight is an error at use time), and `DetectionContext(weights=...)` lets evaluation, analysis and calibration swap tables without touching code. A test parses `features.py` and checks that every feature it can emit has a weight. Weight 0 disables a feature in scoring, but `extract_features(..., keep_zero=True)` still reports it, which is what lets calibration revisit features it once turned off.

**37. How does the dev/test split prevent overfitting?**
`--split` divides external data 70/30 by a salted SHA-256 of the message content (sender, subject, body), not by position. The same message lands in the same split on every machine, whatever the file order or `--limit`, and duplicates, which are common in phishing corpora, can't appear on both sides and leak test answers into tuning. Error analysis defaults to dev, calibration loads only dev, and the README reports only test. The rule for test: look once, after the weights are frozen.

**38. How does calibrate.py avoid fitting noise?**
It loads only the dev split. Inside dev it holds out a further 20% (dev-val, by a different hash) and prints F1 before and after on that held-out part, with a warning not to adopt a suggestion that makes it worse. It searches a coarse grid with coordinate ascent rather than a free optimizer. It adds an L1 penalty pulling each weight toward its hand-set prior, so a weight moves only for a real F1 gain. Features seen on fewer than 30 dev messages keep their prior. Features that guard against attacks the corpus doesn't contain (prompt injection, look-alikes of *our* domains, executive impersonation, bank-detail change, header anomalies, reputation) are frozen: a 2002 corpus has no evidence about them either way, and "no evidence" must not become "weight 0". It writes `weights.suggested.yaml` with the evidence in its header and refuses to overwrite the live file.

**39. Why is error_analysis.py aggregate-only, and what is still unverified?**
The corpora may not be redistributed and personal mail must not leak, so the script prints counts, rates, quantiles and feature names, never a subject, body, address, header value, link or file name. A test runs it on the fixtures and checks that no subject, address, display name, link or attachment name, and no `@` or `http`, appears in the output. That makes the report safe to commit, which is how this round got its evidence without the data. Not verified in the cloud: the effect on the real corpus. Expected by arithmetic: the top false-positive pattern drops from 60.3 to about 4 with list headers and about 24 without, so most of the 970 false positives should fall below 50. The risk is recall: phish whose only evidence was a generic link lose about 21 points. The specific link and attachment signals are meant to recover them, but only the test split can tell. The commands are in the README.

## Operating point and evaluation traps (round 5)

Evidence: the maintainer's local run on the real-corpus test split (30%, fixed content-hash split). Weights v2 at threshold 50: recall 35.0%, precision 98.7%, easy_ham FPR 0.2%, hard_ham FPR 21.2%. At threshold 35: recall 60.8%, precision 97.5%, easy_ham FPR 1.4%, hard_ham FPR 56.1%. The F1-calibrated suggestion: recall 88.4%, easy_ham FPR 38.2%, hard_ham FPR 83.3%.

**40. Your calibration reached 88% recall. Why didn't you ship it?**
Because it flagged 38% of ordinary legitimate mail and 83% of hard ham, so the recall was bought, not earned. Two things went wrong, and both are classic. First, the objective: the test split has about 3 phishing per legitimate mail, and F1 only looks at the positive class, so "flag everything" scores F1 ≈ 0.86, higher than our real operating point (≈ 0.75). An optimizer chasing F1 walks toward that corner. Second, the data: it raised `no_authentication` from 0.01 to 0.45 because 2002 legitimate mail has no DKIM. It learned the year, not phishing. The fix is in the method, not the numbers: `calibrate.py` now maximizes recall subject to easy_ham FPR ≤ 1% (re-deriving the threshold for every candidate, so the class ratio drops out), or a per-category balanced accuracy where each category counts equally. Era and time-zone features (`no_authentication`, `off_hours_send`) are frozen by default, and security features are always frozen. The suggestion is still only a suggestion, judged on a held-out slice of dev before anyone looks at test.

**41. Why is the default threshold 35 and not 50, and what does it cost?**
The threshold is a business decision made from a measured trade-off, not a constant. Moving 50 → 35 on the test split buys +25.8 points of recall (35.0% → 60.8%) for +1.2 points of easy_ham FPR (0.2% → 1.4%) and −1.2 points of precision. Missing a credential-phishing or payment-fraud mail costs much more than quarantining a newsletter, so 35 wins. The cost is real and stated: hard_ham FPR rises from 21.2% to 56.1%, because marketing mail uses the same urgency/payment language as phishing. It's configurable (`PHISHGUARD_THRESHOLD`), and `evaluate.py --sweep` prints 30-60 in steps of 5 so a deployment can choose with numbers. The hard_ham problem is what the hybrid step targets: the 20-50 band holds both the remaining misses and most flagged hard ham, so only that band goes to the LLM. Lowering the threshold also raised a synthetic problem: legitimate supplier invoice reminders scored 36-41 on keywords alone (synthetic F1 fell to 90.7%). Rather than tune the synthetic set, keyword-only signals are softened (0.20 → 0.08) when the sender is both on our trusted-domain list and authenticated (DMARC pass, or SPF and DKIM pass). That is a real-world rule ("invoices from a verified partner are normal business"), it does nothing without configured trusted domains (so the real-corpus numbers stand), and `bank_detail_change` keeps full weight, so a changed-bank-details request from a compromised supplier is still caught. Synthetic F1 is 97.8% at 35. The accepted cost is BEC from a compromised internal mailbox (13 of 200 synthetic BEC), which was already the known weak spot.

**42. Which metric do you report, and why "recall at fixed FPR"?**
Recall at 1% (and 5%) FPR on legitimate mail. It answers the operator's real question, "if I may disturb at most 1 in 100 legitimate mails, how much phishing do I stop?", and it doesn't move when the class ratio changes, whereas a real inbox is mostly legitimate and a public phishing corpus is mostly phishing. The threshold is derived from the legitimate scores: allow ⌊FPR × n⌋ false positives and put the cut just above the next legitimate score, so ties never push FPR over the cap. FPR must be reported per category: a 1% cap on easy_ham can coexist with flagging every hard_ham mail (a unit test shows exactly that), so the tables always print both, and `calibrate.py --max-fpr-hard` can add a second cap.

## Mailbox connectors (round 6)

**43. Where do the connectors live, and how is the read/write split kept?**
In a new package, `phishguard/connectors/`, which is on the read side like `readonly/`. It fetches raw RFC 822 bytes and hands them to `parse_eml` → `PhishingAgent.analyze`, the exact path behind `POST /analyze/eml`, so mail from a mailbox is judged the same as an upload, with the same 2 MB limit. Everything that changes a mailbox is in `phishguard/mutating/remediation.py` and runs only as an Executor handler, so it is reachable only through a gateway grant. `phishguard/worker.py` is an orchestrator like `api.py`: it may import both sides and is the only place a verdict turns into a `gateway.submit()`. `tests/test_isolation.py` holds the connectors package to the same three checks as `readonly/`: an AST scan for imports of `mutating`/`api`/`worker`, the runtime import closure of every connector module, and a full scan with `phishguard.mutating` blocked by an import hook. The direction is one-way by design: remediation may reuse the connectors' HTTP and OAuth code, never the reverse.

**44. Why minimal read scopes, and why separate write credentials instead of one token with both?**
A scanner holding a token that can delete mail is a much better target than one that can only read. Reading uses `gmail.readonly` and Graph `Mail.Read`, and remediation needs `gmail.modify` / `Mail.ReadWrite`. These are separate config sections (`auth` vs `remediation.auth`) with separate token files and separate `--authorize --write` consent, and the write token isn't even loaded unless `remediation.enabled` is true. So a read-only deployment can't be talked into changing mail, even by a bug in our own code. IMAP has no scopes (an app password can do everything), so there the guarantee is ours, not the provider's: reads open the folder with `EXAMINE` (the server enforces read-only) and fetch with `BODY.PEEK[]` (no `\Seen` flag). Tests run the real `imaplib` against a fake server and assert that neither `SELECT`, nor `STORE`/`MOVE`/`EXPUNGE`, nor any flag change happens on the read path. For Gmail and Graph the fakes record methods, and the read path must be GET-only. One exception is documented: creating push subscriptions (`users.watch`, `POST /subscriptions`) is a POST under the read scope and changes no mail.

**45. Which mailbox actions need MFA, and why not all of them?**
If every quarantine needed a human code, nobody would turn remediation on, and phish would sit in the inbox until someone acted, which is worse. So the rule follows blast radius and reversibility. One message moved out of the inbox, labeled, or given a banner copy is reversible and contained: it runs automatically, and each one is in the hash-chained audit log. More than 10 messages in one request (bulk) needs MFA, because that's how a compromised caller would wipe an inbox. Delete always needs MFA: it destroys evidence, and even "Trash" expires. Restore always needs MFA: releasing a quarantined phish into the inbox is exactly what an attacker, or an LLM talked into it by the mail, would want. The policy fails closed: missing, non-list or oddly shaped message ids require MFA. Provider ids are opaque base64-like strings that can contain "bank" or "wire" by chance, so after a strict character check they are excluded from the content scan, while every other param (labels, mailbox names) still goes through it. That is why a mailbox named "payroll" gets its automatic actions held for MFA: fail-safe, and documented.

**46. How do you add a warning banner when providers won't let you edit a received message?**
Gmail messages are immutable, Graph only lets you edit drafts, and IMAP has no edit. The honest options are to leave the original alone and add a label/category, or to insert an annotated copy and move the original out of the inbox. For `banner` we do the second on Gmail (`messages.insert`) and IMAP (`APPEND`): the copy carries a visible warning on every text part and an `X-PhishGuard-Verdict` header, attachments are untouched, and the original goes to quarantine so nothing is lost. On Graph we refuse with a clear `NotSupported` (the Executor reports `ok: false`, never a fake success) and recommend `label` + `quarantine`. The copy is new mail the user didn't receive from the sender, which is why banner is opt-in and never the default action.

**47. How are scans incremental and idempotent across crashes, re-lists and renumbering?**
Each provider has a native cursor: Gmail `historyId`, Graph `deltaLink`, IMAP `UIDVALIDITY` + last UID. The scanner stores the new cursor only after every message of the batch has been recorded as seen. When a batch is cut by `limit`, the cursor doesn't move past mail we didn't return: IMAP advances to the last processed UID, and Gmail/Graph keep the old cursor. Re-reading is harmless because the seen set has two keys: the provider id and the SHA-256 of the raw bytes. The content key catches IMAP renumbering (`UIDVALIDITY` change), the same mail delivered twice, and the full re-list we do when Gmail history or a Graph delta token has expired (404 / 410). "At least once fetched, exactly once scanned" is the guarantee. The test suite checks each of those cases.

**48. What happens to mail too large to scan?**
It is reported, never silently passed. A phish padded past the size limit must not come back as "clean". Gmail and IMAP check the size before downloading (`sizeEstimate`, `RFC822.SIZE`), and Graph streams `$value` and stops at the limit, so a 30 MB message costs a header, not 30 MB of memory. The verdict status is `too_large` with `is_phishing = None`, it's recorded as seen, and the CLI prints it as `TOO_LARGE`. Not auto-quarantining it is deliberate: big legitimate mail (scans, decks) is common. A follow-up could route `too_large` to a label for human review.

**49. How do you respect rate limits without stalling, and why the host allow-list?**
`RetryingClient` retries 429 and 5xx, plus Gmail's 403 `rateLimitExceeded`, which a naive client treats as a permission error. It honors `Retry-After` in both its forms (seconds and HTTP date), else uses exponential backoff with jitter, bounded by `max_retries`. If a provider asks for a wait longer than `max_delay`, it raises `RateLimited` and the worker pauses only that mailbox until then, instead of blocking every other mailbox. A 401 triggers exactly one token refresh and retry. Every request URL must be HTTPS on an allow-listed host, checked before sending: Graph pagination and delta links come from the server, and following a tampered link to another host would hand it our bearer token. A test proves nothing is sent in that case.

**50. How are push notifications trusted?**
They aren't trusted with anything that matters. A valid notification only writes a "scan this mailbox soon" row that the worker picks up, and the mail itself is still fetched with our own credentials. Forging one gains at most an extra scan. They are still authenticated, because the endpoints are public. Graph: the subscription handshake echoes `validationToken` as `text/plain` with `nosniff`, and each notification's `clientState` must equal the per-mailbox secret (constant-time compare). Gmail/Pub/Sub: the push carries a Google-signed OIDC JWT. We pin `alg` to RS256 (rejecting `none` and the HS256-with-public-key confusion), verify the signature against Google's JWKS, and check issuer, audience, expiry/issued-at with 60 s leeway, and the push service account's verified email. An unknown `kid` refreshes the key cache at most once a minute, so forged tokens can't turn us into a request amplifier against Google. These routes live in their own router, mounted by a 6-line change to `api.py` only when configured, and they don't use `X-API-Key` (providers can't send it). Everything else in the API still requires it.

**51. How do you keep OAuth tokens and app passwords out of logs, audit and output?**
Four layers. Sources: secrets come only from an environment variable or a file outside the repository that isn't readable by group/others; the config file holds `*_env`/`*_file` pointers and rejects inline `password:`/`client_secret:` keys. Storage: refresh tokens are written atomically with mode 0600 in a 0700 directory. Masking: every secret loaded, minted or received from a token endpoint is registered, and `redact()` plus a logging filter mask it wherever it might surface (exception messages, provider errors, executor errors, CLI output). Data minimization: verdicts written to logs and the scan DB contain no subject, sender or body (`Verdict.public()`); the CLI shows subject and sender only on the user's own terminal and hides them with `--redact`. A test pushes a refresh token, client secret and access token through the CLI, the worker, a deliberately leaky log line and the audit chain, and asserts none appears. The limit: redaction only masks values it has seen, so a secret that never passed through these loaders (e.g. pasted into a log by hand) is not covered.

**52. What was tested, and what wasn't?**
Tested, with no network: Gmail and Graph REST behavior through `httpx.MockTransport` fakes (pagination, history/delta cursors, expiry fallbacks, size limits, 401 refresh, 429/503 backoff, write endpoints), IMAP through a real-socket fake server driven by the real `imaplib` (EXAMINE/PEEK, UID ranges including the `N:*` edge case, UIDVALIDITY change, XOAUTH2, IMAP ID, MOVE/STORE/APPEND, implicit TLS with certificate verification against a generated CA), OAuth flows (refresh rotation, service-account RS256 JWT verified with the public key, client credentials, device code with `slow_down`, PKCE loopback with state check), webhook token forgeries, and the worker end to end. Not tested: real Google, Microsoft or IMAP servers. No accounts or network access were available, so details such as the exact Graph delta `$filter` support, Google's consent-screen behavior, or a provider's IMAP quirks may need adjusting on first contact. The setup guide tells users to start read-only for exactly that reason.
