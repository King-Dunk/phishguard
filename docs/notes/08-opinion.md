# 08 · 观点：给 AI 代理权限之前，先假设它会被骗

做完 PhishGuard，我最大的结论只有一句：**AI 代理的安全边界，应该画在它"能做什么"上，而不是画在它"能不能分辨"上。**

## 1. 注入是防不完的

提示词注入的本质是：模型分不清"数据"和"指令"。只要模型需要读外部内容（邮件、网页、文档），攻击者就能往里面写指令。新的说法永远列不完：伪造系统消息、套学术研究场景、角色扮演、换语言、换编码。用关键词去拦，或者用另一个模型去识别，都只能降低概率，变不成边界。

## 2. 所以要回答的问题变了

不是"怎么让 AI 不被骗"，而是"AI 被骗之后，最坏会发生什么"。在 PhishGuard 里，答案是：

- 它想转账，但手里没有转账工具；
- 它想说"这封是安全的"，但它的分数只能往上加；
- 它想写一段话说服用户，但这段话被当成不可信的输出；
- 真正动钱的那一步，要人用两种方式、针对那一笔具体的操作来确认。

## 3. 人的确认也需要设计

"让人确认"不是万能的，至少要做到三点：

- **绑定具体的操作**：批准的必须是屏幕上那一笔，金额或收款人一改就失效。
- **用钓不走的验证方式**：密码和安全问题可以被同一个钓鱼页面一起骗走；通行密钥绑定真实网址，骗不走。
- **限制次数，记录一切**：失败计数什么时候清零，本身就是攻击面。

## 4. 检测仍然有用，但分工要清楚

规则和模型负责"尽量多抓、少打扰"，权限设计负责"漏掉了也不出事"。在我的测试里，从被盗的真实邮箱发来的诈骗（T4），检测率是 0%；而供应商真的换了银行账户的正常邮件，100% 被误报。它们本来就长得一样，只能靠流程解决：两种验证、收款账户冷静期、打电话给供应商核实。

## 5. 诚实的评估比好看的数字更有价值

README 上 66% 的召回率看起来还行，拆开才发现主要靠 20 年前的老式钓鱼撑着，2024–25 年的只有 47%；真实邮箱的误报率是 20%。我选择把这些都写在首页，因为一个只报好数字的安全项目，本身就不可信。

## 6. 这个项目作为产品没有用，但思路可以搬走

Gmail 已经过滤掉了大部分钓鱼，20% 的误报率也没法日常使用。它的价值在于设计。任何既要读外部内容、又能动钱或改账户的 AI 代理，比如邮件助手、财务助手、客服，都可以用同一套办法：

1. 读和写分开，读的那边拿不到写的能力；
2. 什么算敏感，写死在代码里；
3. 敏感操作要人用强的验证方式，针对具体的操作来确认；
4. AI 的所有输出都当作不可信的输入；
5. 用红队验证"后果有没有发生"，而不是验证"手法有没有被认出来"。

## 7. 我还没想清楚的

- 如果 AI 必须有写权限才有用（自动回复、改日程），哪些操作可以不经确认？"可以撤销"是不是一个足够好的标准？
- 如果每一笔都要确认，用户会不会麻木到不看就点？MFA 疲劳攻击利用的正是这一点。
- 进程内的隔离在真实系统里不够。拆成独立的服务之后，身份和授权应该怎么设计？
