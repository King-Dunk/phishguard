# 06 · 评估：这些数字该怎么读

> 一句话：好看的总数会骗人。要按年份、来源、定制程度拆开看，而且只引用没调过参的测试集。

## 用了哪些数据

| 数据 | 内容 | 用途 |
|---|---|---|
| SpamAssassin（2002–03） | 正常邮件：easy_ham，以及像营销邮件的 hard_ham | 测误报 |
| Nazario（2004–2025） | 真实钓鱼邮件，按年份分文件 | 测召回率，看年代变化 |
| Phishing Pot（大多是 2023–26） | 蜜罐收到的真实恶意邮件，随机抽 3,000 封 | 独立的新来源，从没用来调参 |
| 分层合成集（T1–T4） | 按 NIST Phish Scale 生成的四个定制等级，每级 100 封钓鱼和 100 封相似的正常邮件 | 看检测在哪里失效 |
| 我自己的 Gmail | 199 封普通邮件，没有钓鱼 | 测真实环境的误报 |

## 防止"自己骗自己"的规矩

1. **dev 和 test 分开**：公开数据按邮件内容的哈希（加盐）分成 70% dev 和 30% test。调参、分析错误只在 dev 上做，对外只报 test。用内容哈希而不是按顺序切，是为了让任何一台电脑分出来都一样，而且重复的邮件不会同时出现在两边。
2. **test 只看一次**：看过的 test 再拿来调参，它就变成了 dev。老实说，这个项目的 test 已经看过好几次，所以文档里写明了它更接近 dev 的数字。
3. **报置信区间**：样本少的时候，一个百分比的误差很大。比如 2024–25 年只有 282 封，47.2% 的 95% 置信区间是 41.4% 到 53.0%。这里用 Wilson 区间，因为样本小、比例接近 0 或 100% 时，它比普通公式可靠。
4. **独立来源**：Phishing Pot 从没参与调参。下载的每个文件都和它在 git 里的哈希核对过，抽样用固定的随机种子，别人可以复现。

## 两个容易踩的坑

- **年代偏差**：正常邮件是 2002 年的，那时还没有 DKIM 和 DMARC；钓鱼邮件是后来的。于是"没有认证信息"这个特征在数据里几乎等于"年份"。自动调参器真的学会了这一点，把它的权重从 0.01 调到 0.45：召回率到了 88%，但会把 38% 的正常邮件标成钓鱼。这个建议被否决，这个特征也被冻结。
- **F1 会随比例变**：test 里钓鱼邮件大约是正常邮件的 3 倍。一个"全部判成钓鱼"的模型，F1 能到 86%，比真实模型还高，却毫无用处。所以改用"固定误报率下的召回率"。

## 分层：NIST Phish Scale

NIST Phish Scale 用两件事衡量一封钓鱼邮件有多难识别：

- **破绽（cues）**：看得出来的问题，比如认证失败、可疑链接、语法错误、催促的语气。
- **前提契合度（premise alignment）**：内容和收件人的实际工作有多吻合。

四个等级（规则单独打分，阈值 35）：

| 等级 | 特点 | 平均破绽数 | 抓到 | 不配置供应商和高管名单时 |
|---|---|---|---|---|
| T1 群发 | 破绽多 | 7.6 | 88% | 88% |
| T2 冒充品牌 | 攻击者自己的域名、认证都通过、链接放在免费托管网站 | 4.5 | 58%（二维码版本 0/21） | 58% |
| T3 精准针对 | 冒充供应商或高管 | 3.9 | 100% | 59% |
| T4 被盗的真实邮箱 | 真实账户、真实的往来邮件，契合度最高 | 1（每封都只有 1 个） | 0% | 0% |

最重要的一个结果：埋了 0–1 个破绽的钓鱼，一封都没抓到（0/100）。这说明**只看内容的检测，本质上是在找破绽**，没有破绽的钓鱼它就看不见。与此同时，对照组里"供应商真的换了银行账户"的正常邮件，100% 被误报，因为它和 T4 的诈骗邮件长得一样。

## 结论怎么读

- README 上 66% 的总召回率，主要是靠 20 年前的老式钓鱼撑起来的：2004–07 年 78.7%，2024–25 年只有 47.2%。
- 越新、越定制化，规则越抓不住。新的钓鱼邮件更多能通过发件认证：2024–25 年有 65% 的 DMARC 是 pass，2004–07 年是 0%。
- 合成数据是"地图"：告诉你检测在哪里失效，不告诉你真实世界里这种情况有多常见。因为生成器、规则和红队都是同一个人写的。
- 这恰好就是整个设计的理由：检测会漏，所以钱的安全不能靠检测。

## 我学到的

- 先问"这个数字是在什么数据上、什么条件下测的"，再看数字本身。
- 把失败的数字写进首页，比只写好看的数字更有说服力。
